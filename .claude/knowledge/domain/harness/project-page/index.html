pAIchart Pipeline Harness

Goal-Directed Multi-Agent Delivery for Domain-Scoped Outcomes
Steve Terry (pAIchart)
[Paper] [Live MCP Endpoint] [Platform] [Contact]

Large language models are remarkably capable on isolated tasks. Producing structured, customer-facing deliverables — security assessments, compliance audits, architecture reviews — requires something more than a capable base model. It requires an orchestration layer that decides what to do, who should do it, how knowledge flows between specialists, and whether the result is good enough.

The pAIchart Pipeline Harness is a production implementation of that orchestration layer. Given a single sentence — "Assess cloud security posture and produce remediation roadmap" — the harness decomposes the objective into typed specialist tasks, assigns the right specialist to each, wires dependencies, executes in order with automatic context chaining, gates quality via confidence-scored completion loops, and reports deliverables. No manual intervention.

Live system. Unlike most multi-agent orchestration papers, the primary artifact here is not a code release or a benchmark. It is a running production server at https://paichart.app/mcp that you can connect to directly from Claude Desktop, ChatGPT, Gemini, or any MCP-compatible client. New users auto-register via GitHub OAuth with a demo role. See the Try It section for the one-line configuration.

Approach

The Pipeline Harness addresses six capabilities we argue are essential for goal-directed autonomous delivery — and which, to our knowledge, no existing system combines:

CapabilityHow we implement it
1. Task decompositionA meta-agent (claude-sonnet-4-5) reads the POV context and decomposes a one-sentence objective into 3–7 typed tasks with explicit dependencies.
2. Typed specialization8 functional types (ARCHITECT, BUILDER, ANALYST, REVIEWER, OPERATOR, DOCUMENTER, ORCHESTRATOR, GENERALIST) decoupled from domain categories. 17 specialist templates map to these types.
3. Knowledge transferA pre-execution hook injects complete predecessor output into successor prompts as structured markdown. No summarization, no "telephone game" degradation.
4. Self-evaluationEvery agent reports a confidence score (0–100). The harness uses these as quality gates: ≥70 accept, 50–69 retry with feedback, <50 escalate.
5. PersistenceBounded re-execution (max 2 retries per task) with hypothesis-driven feedback. Self-completion guard prevents false success reporting.
6. Context awarenessEvery prompt is grounded in a persistent POV record — customer, objective, solution, team, compliance frameworks, execution history.

Architecture

Dual-Mode Operation

The harness operates in two auto-detected modes:

  • CREATE mode. User gives the harness a one-line objective. The harness creates a new pipeline stage, decomposes the objective into typed tasks, assigns specialists, wires dependencies, and executes. Used when the user wants the harness to design the pipeline.
  • ORCHESTRATE mode. User creates work tasks themselves and adds a PIPELINE task in the same stage. The harness detects the siblings, infers templates from task descriptions, wires dependencies, and executes. Used when the user designs structure and wants the harness to handle execution.

Mode detection is a simple rule: if the harness finds siblings in its own stage, it is in ORCHESTRATE mode. Otherwise it is in CREATE mode. Both modes share the same execution engine, the same context chainer, the same confidence loop, and the same self-completion guard.

Automatic Context Chaining

When a task has dependencies, the execution engine invokes the context chainer as a pre-execution hook before starting the LLM call:

  1. For each dependency task, read the latest successful execution's result.json
  2. Extract finalResponse, confidenceScore, qualityMetrics
  3. Render as structured markdown in prompt section §6: 
    ## Pipeline Context (from previous tasks)

### Previous Task: Design data migration strategy
- Agent Role: solution_architect
- Confidence Score: 88/100

**Output:**
[complete 26K-character deliverable — no summarization]

**Use the above output to inform your work. Build on
what was produced — do not repeat or re-derive it.**

The agent never knows context chaining is happening. It simply finds the relevant context already in its prompt. This eliminates an entire class of coordination failures that arise when agents must explicitly fetch upstream context — in our earlier design, omissions were common and context fidelity depended on prompt compliance. The pre-execution hook removes agent behavior from the critical path entirely.

Two Execution Paths

The same MCP actions are served through two different code paths:

PathLanguageUsed byCharacteristics
Embedded TypeScript (in-process) Agent execution engine (harness + specialists) No HTTP, no rate limiting, lean Prisma queries, JWT passed in-memory
MCP Server JavaScript (external) Claude Desktop, ChatGPT, Gemini, CLI clients HTTP streamable, OAuth/API key auth, 300 req/min rate limiting, fuzzy matching, friendly error formatting

Handlers in the two paths are not duplicates — they serve different clients with different needs. The TypeScript handlers are lean because agents send exact parameters and reason over raw errors. The JavaScript handlers are rich because humans in Claude Desktop need fuzzy template matching and friendly errors.

Emergent Behavior

In Experiment 4 (cloud migration readiness, clean POV) the meta-agent produced two distinct behaviors that we did not explicitly prompt:

Non-linear dependency graph. Rather than decomposing the objective into a linear chain, the agent reasoned about task independence and produced a graph with three parallel roots feeding into a synthesis task:

Task 1 (Infrastructure)  ─┐
Task 2 (Security/AU)     ─┼─→ Task 4 (Strategy) → Task 6 (Report)
Task 3 (Operational)     ─┘          ↓
                          Task 5 (Cost-Benefit)

The harness prompt describes only decomposition rules and constraints (3–7 tasks, typed specialists, explicit dependencies). It does not describe parallel topologies, multi-predecessor synthesis, or dependency graph optimization. The meta-agent produced these behaviors independently.

Cross-phase stage distribution. The agent created three new stages across two phases of the POV, mapping task kinds to POV lifecycle phases (assessments in Execution, synthesis in Review) without being told which phase to use for which purpose.

Regional framework propagation. The POV specified Australia. The Security task description explicitly referenced ASD Essential Eight, APRA CPS 234, and the Privacy Act 1988 — compliance frameworks specific to Australian financial services. The harness prompt does not enumerate regional frameworks; this emerged from context.

Security

pAIchart is a remote multi-user MCP server. The Anthropic MCP Security Best Practices specification enumerates a set of attack vectors with normative mitigations (MUST and SHOULD). Because we are deployed in production with real authentication and real user data, we document compliance per attack vector rather than claim blanket certification.

Attack vectorOur implementation
Confused deputy OAuth proxy implements per-client consent stored server-side, state validation with exact matching, __Host- prefix cookies, exact redirect URI matching (no wildcards)
Token passthrough MCP server mints own tokens with explicit audience binding. Does not forward external tokens to downstream services.
SSRF Outbound traffic HTTPS-only, limited to allowlisted endpoints. Primary remote-server variant — not a local client exposure.
Session hijacking Session IDs via crypto.randomUUID(), bound to user ID derived from JWT. All inbound requests verified via requireAuth middleware.
Scope minimization Least-privilege default: new users auto-register with DEMO_USER role (demo POVs + personal sandbox). Elevated roles require out-of-band approval.
Local compromise N/A — remote HTTP server, not a local stdio binary.
